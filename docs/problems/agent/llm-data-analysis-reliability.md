# LLM 数据分析可靠性：模型能力问题还是使用方式问题（2026-10-17）

> 范围：定时报告流水线 + 对话式数据分析沙箱的数值可靠性。
> 状态：结论已定，架构不回退；待改项列在第五节，未实施。

## 一、问题与结论

**起因**：2026-10-15 故障报告正文写「10 月 11 日（5 起）回落，虽低于本期峰值但**高于** 10 月 5 日水平」，
而 10-05 实际是 6 起。模型手上明明同时有 5 和 6，仍然把大小关系写反了。

由此引出的问题是：**是不是模型做数据分析就不可靠，以后每次都可能出问题？**

**结论**：

1. 不可靠的不是「模型不能分析」，而是「让 LLM 在自然语言里做**数值计算与精确比较**」。
   定性判断（波动特征、原因推测、风险与动作）模型做得很好；心算、做差、比大小、换算单位
   属于它的硬伤，且**能力提升不会消除**——这是自回归生成与符号计算的结构性差异。
2. 这**主要是使用方式问题**。业界没有靠"换更强的模型"解决，而是靠架构规避：
   **把计算移出模型（代码解释器/语义层），把解读留给模型**。
3. 我们的定时报告误在「计算已经由 pandas 做完了，但比较又交回给模型做了一遍」。
   2026-10-16 起已改为：数据层统一日期轴 + 事实层把比较预先算好 + 趋势章确定性拦截闸。
4. **不能由此退回「全文都让模型自己看数据」**。让模型自行分析只会把错误从"比较写反"
   扩大到"统计口径、对齐、聚合全错"，且不可复现、无法审计。

## 二、证据

| 证据 | 内容 | 指向 |
|------|------|------|
| 心算准确率 | 公开评测中，真实计算任务的端到端准确率约 45%~63%，错误集中在计算步骤与数值精度，而非理解题意 | 计算不是语言模型的强项 |
| 本次事故 | 模型上下文里同时有 `10-05 = 6`、`10-11 = 5`，仍生成「5 高于 6」 | 给对数字也不保证比较正确 |
| 热力图事故 | 直接把按位置对齐的 `dcs/levels/matrix` 喂给模型，`惠州A3分部 = [0,4,10,0]` 被解读成"4 级事件分布密集"，真实密集的是名字相近的 `A3分部 = [1,5,10,1]` | **输入表示**本身会诱发幻觉（intrinsic hallucination） |
| 架构收益 | 定时报告改确定性流水线后：80~95 秒（原 8~33 分钟）、8 次模型调用（原 25 次）、统计与图两次运行逐字节一致 | 计算与解读分离后，结果可复现 |

后两条说明：**即使数字正确、即使模型看得见，只要还要求它在正文里自行组织比较/对齐，
同类错误就会复发**。这正是加事实化与拦截闸的理由。

## 三、业界三种成熟形态

| 形态 | 代表 | 做法 | 适用 |
|------|------|------|------|
| 代码解释器 / 沙箱 | ChatGPT Advanced Data Analysis、Claude code execution、DifySandbox、DeerFlow | 模型**写代码**做计算，只读代码返回的结果 | 开放式、探索式分析 |
| 语义层 / 指标层 | Cube、AtScale、dbt Semantic Layer、Snowflake Cortex Analyst | 指标定义与计算下沉到语义层，模型只负责选指标、组织解释 | 指标口径固定、要求一致性 |
| 确定性工作流 + LLM 解读 | Anthropic《Building Effective Agents》中的 workflow 范式 | 取数、统计、出图由代码完成；每章只让模型写解读 | 形态固定、周期性产出（报告） |

三种形态的共同点：

- **模型不直接算数**。计算由代码或语义层完成，模型只消费结果。
- **给模型的数据必须是带标签、无歧义的表示**。不能把"靠位置对齐的矩阵"丢给它自己数。
- **仍要审计与复算**。代码执行也可能算错东西（逻辑/口径），需要断言、单测、人工抽检。

## 四、我们的架构映射与决策

| 场景 | 采用的形态 | 现状 |
|------|-----------|------|
| 定时报告（事件/故障/变更/问题/阈值） | 第三种：确定性工作流 + LLM 逐章解读 | 已落地：`report/common.py::_window_trend`、`report/facts.py`、`report/trend_guard.py` |
| 对话式数据分析 | 第一种：`analysis_load` 物化全量 → `analysis_exec` 沙箱跑 pandas → 模型解读 | 已落地，见 `tools/analysis_tools.py` |
| 指标口径治理 | 第二种：尚未引入 | 当前靠 compute 层固定口径 + 单测 |

**明确不做的决策**：不把定时报告退回「agent + 沙箱」形态。理由：

- 代码每次由模型重写，口径会漂移，两份报告的数字不可比；
- 固定开销约 29.5k tokens、约 25 次主模型调用，上游不稳时成片失败；
- 统计与图无法做到两次运行逐字节一致，出问题无法二分定位。

## 五、待改清单（尚未实施）

### 5.1 趋势章：让"引用"比"推理"更省事

当前事实层已经给出总量对比、逐日对位、排序、零单日、峰谷，但模型仍可能为了写"趋势分析"
而自行做比较。改进方向：

- `report/facts.py::_trend_facts` 增加**日均值（分母＝窗口自然日数）**与「高于/低于日均的天数」，
  把最常见的派生比较也预先算好；同时给逐日明细表，减少模型自行归纳的动机。
- `report/narrate.py::_BRIEFS['trend']` 从「禁止自行比较」改为
  「比较只引用原句；波动特征/原因/需盯时段等定性分析可自由发挥」，避免模型因"没东西可写"
  而绕开约束。
- `report/narrate.py::_SECTION_SYSTEM` 第 3 条要求"特征必须落到园区或部门"，
  对时间序列章是错误引导（趋势变化不一定是空间差异），需按章节角色区分。
- `report/trend_guard.py::_ANCHOR_RE` 补日均锚点（`本期日均`/`日均`），
  使「高于本期日均」这类新增说法也纳入校验。

### 5.2 对话侧：禁止正文心算

`core/agent/prompts.py` 元规则 6 目前只要求"统计走全量物化 + `analysis_exec`"，
没有明说"正文数字必须来自工具返回"。需补充：

- 数字与比较必须直接来自 `analysis_exec`/`analysis_load` 的结果；
- 正文不得做减法、比大小、单位换算、百分比心算；
- 需要派生指标时，把它写进脚本让 pandas 算，而不是在自然语言里推。

## 六、边界（必须说清）

1. **沙箱解决"算错"，不解决"算错东西"**。代码执行只保证算术正确；口径错误、对齐错误、
   过滤条件错误仍是逻辑问题。本次趋势轴错位就是一个 pandas 逻辑 bug，换成模型写代码同样会犯。
   因此报告的 compute 层必须有单测与断言，不能因为"进了沙箱"就免检。
2. **`trend_guard` 只覆盖趋势章**。其余矩阵章（园区×级别、级别×阶段、热力图等）目前靠
   事实化 + `依据` 编号校验，**没有**等价的数值关系拦截闸。
3. **百分比、区间、模糊表述不做确定性校验**。这类表述与具体数值的关系不唯一，
   强校验会误杀正确结论。宁可漏拦，不可误杀。
4. **模型能力的上限仍在**。架构只能把"可证明为假"的错误压住；语义层面的错误
   （把正确的数字解释成错误的业务结论）只能靠人工抽检与单测覆盖，无法完全自动化。

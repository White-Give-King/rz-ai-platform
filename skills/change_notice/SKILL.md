# 每日变更统计

以**园区日常运维群**里人发送的变更通知为入口：一条 = 一次变更（开始/完成通知按**变更窗口**配对；
同一工单跨多次变更分别计数），记录园区 × 数据中心的**变更类型 / 维护事项 / 执行状态**。
**机器人卡片不计**，只统计人发的消息。

## 工作流

1. 调 `change_notice_report(date, start, end, parks, sync, export_excel)`。它是**确定性工具**：
   窗口由服务端按**自然日**算，**不要自己换算时刻或改口径**。
   回答开头**必须复述返回的 `window_note`**（写明实际截止时刻）。**今天/含今天按「到此刻」的滚动
   窗口统计**，同一问题在不同时刻问条数会变，不复述截止时刻用户会以为统计错了。
   再给各园区条数（`overview` / `summary_markdown`）。
2. 按返回里的 `mode` 交付（**不要自己另存文件、不要改写 url**）：
   - `inline`（≤20 条）：先给 `summary_markdown` 汇总表，再**原样输出 `table_markdown`**（服务端按固定列
     渲染好：园区/数据中心/变更类型/维护事项/执行状态/计划开始/计划结束/实际开始/实际结束/工单号/
     变更等级/现场负责人/现场负责人等级/消息时间，空值已是「—」），再**原样输出 `file_tag`**
     （可搜索/排序的交互表格）。只在表格前后各加一两句结论，**不要自己重排、合并、增删列，也不要另造表**。
   - `records`（>20 条）：先原样输出 `summary_markdown` 汇总，再原样输出 `file_tag` 打开交互表格，
     补一两句结论（条数、各园区分布）；**不要**因为没文字明细就去拉原始群消息。
   - `export`（用户明确要 Excel）：原样输出 `file_tag`。
   - `empty`：按 `note` 说明当天没有变更记录，**不要**推断「机器人收不到消息」。
3. 返回 `sync_error` 时如实说明「本次按库里已有消息统计」，不要把同步失败讲成没有数据。

**Excel 只在用户明确要时出**：说「查一下 / 统计一下 / 表格」都按默认（文字），
只有明确说「导出 / Excel / 给个文件 / 下载」才传 `export_excel=true`。

## 参数

| 参数 | 含义 |
|------|------|
| `date` | `YYYY-MM-DD`，统计该自然日。不传 = 今天 |
| `start` / `end` | 日期区间（`YYYY-MM-DD`，含首尾）。不能与 `date` 同时传；只传一个 = 单日 |
| `parks` | 园区名，逗号分隔（如「廊坊」「廊坊,平湖AB」）。留空 = 所有已配置园区合并成一张表 |
| `sync` | 默认 true：先从飞书群补拉该窗口的消息；只想按已入库数据取数时传 false |
| `export_excel` | 默认 false。仅用户明确要 Excel/文件/导出时传 true |

| 用户说 | 传参 |
|--------|------|
| 「今天有什么变更 / 今天的变更统计」 | 留空（默认今天） |
| 「昨天有什么变更」 | `date=<昨天>` |
| 「11 月 19 日的变更」 | `date=2026-11-19` |
| 「11 月 17 到 19 日」 | `start=2026-11-17, end=2026-11-19` |
| 「廊坊昨天的变更」 | `parks=廊坊` |

## 口径（回答用户时照此解释）

- **一行 = 一次变更**：同一工单内按**变更窗口**（计划开始优先，缺失用实际开始，归一到分钟）分条——
  窗口相同的重发才计一条；窗口不同（同一单跨班次做两轮）各计一条。完成通知先配同窗口，
  配不上并入该工单最近一条未完成。合并口径：文本取首个非空、时间取最早、状态取最高
  （已完成 > 已取消 > 进行中）。
- **只统计人发送的消息**：机器人卡片（`sender_id_type='app_id'`）一律不计；共享部门账号（open_id）算人。
- **自然日、按消息发送时间归属**：不是班次（与事件统计表不同）。历史日期窗口是 `Asia/Shanghai`
  00:00–24:00；**今天只算到当前时刻**（定时预设 18:10 跑，即当天 00:00 ~ 18:10）。
- **变更类型**按通知里的等级分档：紧急/临时 → 临时新增紧急变更；高/高风险 → 高风险变更；
  中/中级 → 中风险变更；低 → 低风险变更；没有标注等级的记「未标注」，
  **不要**自己按标题猜风险档。
- **执行状态**：见到完成/结束 → 已完成；只有开始 → 进行中；含「取消」→ 已取消。
- **现场负责人**列只含**姓名**：优先取负责人性质标签（变更负责人/现场负责人/相关负责人/现场联系人），
  没有才用值班工程师兜底；电话/工号一律剥掉，多名以「、」拼接。查不到姓名就留空，
  **不要**把电话或标签词当成负责人。
- **现场负责人等级**取自综合管理平台人员档案（报文本身没有职级）：匹配不到/查不到就留空，
  档案有此人但无等级写「无评级」。**不要**自己按姓名推断、补全或猜测等级。
- **等级匹配**（逐级对应：低风险→初级及以上、中/高风险/紧急→中级及以上、未标注→无法判定；
  多人取最高职级）**只在页面展示**，对话工具输出仍是 14 列、不含该判定。
- **统计范围**：纳入**廊坊式 `【变更开始/完成-通知】`**、**方括号式
  `【变更开始/完成-<标题>】`（佛山/重庆）** 与**平湖编号列表维护通告 `【…维护通告】开启`** 三种报文；
  平湖「位置」是楼宇字母，按 **Y楼→A1、Z楼→A2、W/W楼→M3M4** 映射数据中心，无工单号按
  「园区+数据中心+标题+日期」配对。惠州的维修变更不算正常变更，平台直接丢弃。
- **数据边界**：各园区是 2026-11-19 起才按新流程发变更通知，更早日期通常是空表（属数据事实，
  不是故障）。惠州（维修格式不纳入）、佛山（起点后暂无方括号报文）、巴淡等单量偏少或为 0
  都属正常，**不要**据此推断消息丢失。

## 边界

- 只能读**机器人已加入**的飞书群；进群前的历史消息大概率拉不到。
- 只统计 `CHANGE_NOTICE_FEISHU_PARK_CHATS` 登记的园区群；未配置群的园区会被直接排除
  （点名了未配置的园区会返回错误，不静默丢数据）。
- 统计由平台确定性解析，**不要**用 `analysis_load` 或沙箱重新统计同一批消息；也不要用
  `group_message_search`（只查应急/事件通报群，查不到变更）或 `fetch_group_messages`（返回原始
  消息、条数对不上）替代——统计一律以 `change_notice_report` 为准。
